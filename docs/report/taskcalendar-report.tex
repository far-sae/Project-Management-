\section*{\color{accent}Abstract}
\addcontentsline{toc}{section}{Abstract}

\noindent
\tc{} is a multi-tenant Software-as-a-Service product that
consolidates five capability domains, traditionally bought as separate
tools, into a single workspace: \emph{(i)} project and task
management, \emph{(ii)} a sales CRM with multi-pipeline deals,
\emph{(iii)} a declarative automation engine, \emph{(iv)} AI
assistance via a sales agent and embeddable AI Blocks, and \emph{(v)}
chat-bot control on both Telegram and Meta WhatsApp.

The platform is implemented as a React single-page application
served from Vercel with a Supabase backend (PostgreSQL with
Row-Level Security, Realtime, Storage, and Deno-based Edge
Functions). Identity is managed by Firebase Auth and bridged into
Supabase JWTs. Outbound integrations include Google Calendar/Meet,
Gmail, Slack, Stripe Billing, and Cloudflare Turnstile, with
OpenAI's \code{gpt-4o-mini} powering all natural-language parsing.

This report documents the system in enough depth that a reader new
to the codebase can understand each component, the data flow between
them, and the security boundaries that enforce multi-tenancy.
Particular attention is paid to two surfaces \dash{} the
\textbf{Clients module} and the \textbf{Automation engine} \dash{}
which together carry most of the product's value over a pure
task-management tool.

\vspace{0.6cm}
\noindent\textbf{Keywords:}
SaaS architecture, multi-tenancy, Row-Level Security, automation
engine, sales CRM, chat-bot integration, Telegram Bot API, WhatsApp
Cloud API, large-language-model agents.

\section{Introduction}\label{sec:intro}

\subsection{Motivation}

Small businesses today buy specialised tools for each part of the
work day. Asana or Trello cover task management. HubSpot or Pipedrive
cover the CRM. Zapier or Make cover automation. Notion or ClickUp try
to be the connective tissue. The result is a tab-switching workday,
five subscription bills, and data that lives in five different
schemas with no shared model of the customer or the project.

\tc{} is built on a simple thesis: a team of three to ten people
should be able to run all of the above from one product, with one
data model, one billing relationship, and \dash{} crucially \dash{}
one place where automation can reach across project work and sales
work without a glue layer.

\subsection{Objectives}

The platform aims to satisfy six functional goals:

\begin{enumerate}
  \item Provide a complete project-and-task surface (boards, calendar,
    timeline, files, comments, notifications, time tracking).
  \item Provide a complete sales CRM (clients with categories,
    multi-pipeline deals, lead capture forms, lead scoring, contacts,
    notes, deal-scoped activity).
  \item Provide a declarative \emph{when X happens, do Y} automation
    engine with sufficient triggers and actions to replace external
    workflow tools.
  \item Provide AI assistance \dash{} a sales agent for proactive
    suggestions, reusable AI Blocks as action handlers, and intent
    parsing for chat-bot input.
  \item Provide chat-bot input on Telegram and WhatsApp so users can
    capture work without opening a browser.
  \item Operate as a hardened multi-tenant SaaS: RLS on every table,
    encrypted OAuth tokens, audited webhook signatures, plan-gated
    feature access.
\end{enumerate}

\section{System architecture}\label{sec:arch}

\subsection{Layered view}

\tc{} is a five-layer system, sketched in Figure~\ref{fig:layers}.
The browser hosts a React single-page application. The browser
talks either \emph{directly} to PostgreSQL (constrained by Row-Level
Security policies) or to a thin layer of Deno-based Edge Functions
when a privileged operation, a third-party API call, or a webhook
endpoint is required. The Edge Functions in turn read and write to
the same PostgreSQL instance, this time as the \code{service\_role},
which bypasses RLS but is itself constrained by application-level
membership checks.

\subsection{Multi-tenancy}

Every business-domain table carries an
\code{organization\_id uuid} column. Reads are gated by an SQL
policy of the form
\begin{lstlisting}[language=SQL2]
create policy "members read X"
  on public.X for select
  using (public.is_org_member(organization_id));
\end{lstlisting}
where \code{is\_org\_member} reads \code{auth.uid()}. Service-role
code paths use the two-argument variant
\code{is\_org\_member\_for(p\_user\_id, p\_org\_id)} so the chat-bot
webhooks can re-evaluate membership when there is no JWT in context.

\section{The Clients module}\label{sec:clients}

The Clients module is the CRM half of \tc{}. It is gated behind the
\code{crm} feature flag (Advanced plan and above; see
Section~\ref{sec:plans}).

\subsection{Entity model}

Five core tables form the data spine:

\begin{itemize}
  \item \code{clients} \dash{} companies or individuals. Carries
    \code{name}, \code{legal\_name}, \code{industry},
    \code{category} (free text), \code{type}, \code{status},
    contact details, address, \code{annual\_revenue},
    \code{employee\_count}, lead score and band, owner, tags, and a
    \code{custom\_fields jsonb} bucket for tenant-specific columns.
  \item \code{client\_contacts} \dash{} humans associated with a client:
    first/last name, title, email, phone, mobile, primary flag.
  \item \code{client\_notes} \dash{} activity log with
    \code{kind} in \{\code{note}, \code{call}, \code{meeting},
    \code{email}, \code{task}\} and an optional \code{deal\_id}
    introduced in migration 089.
  \item \code{client\_attachments} \dash{} files referenced by Storage
    path.
  \item \code{client\_tasks} \dash{} follow-up tasks
    (\code{todo}/\code{call}/\code{email}/\code{meeting}/\code{followup}).
\end{itemize}

Deals are first-class but live in their own family of tables:
\code{deals} (title, value, currency, stage, probability, expected
close, owner, source, loss reason); \code{pipelines} and
\code{pipeline\_stages} (admin-configurable, with
\code{is\_won}/\code{is\_lost}/\code{required\_fields}/
\code{default\_probability} flags); \code{lead\_scoring\_rules} and
\code{lead\_scoring\_thresholds}; and \code{lead\_forms} (public form
definitions with Cloudflare Turnstile protection).

\subsection{Client categorisation}

\subsection{CSV import with extensible columns}

The importer accepts a canonical 41-column template plus any custom

\begin{enumerate}
  \item User drops a CSV. Papaparse parses; \code{previewClientImportRows}

  \item In the preview step the user can (a) type custom column names
    that aren't in the canonical template, (b) quick-add chips for any

so an industry-specific importer (manufacturing, NGOs, agencies) can
keep arbitrary attributes without a schema migration.

\section{The Automation engine}\label{sec:automation}

The automation engine is the most architecturally interesting part
of the system. It mirrors Monday.com's recipe builder \dash{}
\emph{when X happens, do Y} \dash{} but in a smaller surface area
that integrates tightly with the data model already used by every
other module.

\subsection{Data model}

Four tables, introduced in migration 065:

\begin{itemize}
  \item \code{automation\_recipes} \dash{} the user-defined rules.
    Fields: name, description, \code{trigger\_type},
    \code{trigger\_config jsonb}, \code{conditions[]}, \code{actions[]},
    enabled flag, \code{run\_count}, \code{fail\_count},
    \code{last\_run\_at}.
  \item \code{automation\_events} \dash{} append-only event queue.
    Fields: \code{event\_type}, \code{payload jsonb}, source
    metadata, \code{depth} breadcrumb, \code{enqueued\_at},
    \code{processed\_at}.
  \item \code{automation\_runs} \dash{} per-recipe execution log.
    Status \{success, failure, skipped, partial\},
    \code{action\_results jsonb}, \code{started\_at},
    \code{finished\_at}.
  \item \code{automation\_worker\_heartbeat} \dash{} singleton row
    used for health monitoring (\code{last\_run\_at},
    \code{last\_batch\_size}, \code{last\_duration\_ms}).
\end{itemize}

\subsection{Trigger to action flow}

Figure~\ref{fig:autoflow} sketches the runtime flow. A trigger
(plpgsql AFTER trigger, form submission, or cron tick) appends a
row to \code{automation\_events}. The worker, scheduled every
minute by pg\_cron, pulls a batch of up to two hundred events,
loads the recipes whose \code{trigger\_type} matches, evaluates
each recipe's conditions, and dispatches actions through a pluggable
registry.

Resolvable variables include

\subsection{Loop prevention and safety}

The primary loop guard is per-recipe burst detection: before
evaluating any recipe, the worker counts that recipe's
\code{automation\_runs} in the past 60\,seconds. If the count reaches
100, the recipe is automatically disabled
(\code{enabled = false}) and a \code{skipped} run is written with the
message \code{auto\_disabled\_runaway}. A secondary 1\,000-runs / 24\,h
ceiling catches slower loops.

\subsection{Worker concurrency}

A PostgreSQL advisory lock (\code{pg\_try\_advisory\_lock(0xC8AE0001)})
serialises worker invocations. The cron schedule fires every minute;
if a previous run is still in flight, the new invocation exits
immediately with \code{skipped: already\_running}. A typical run
processes at most 200 events at $\sim 50$\,ms each, comfortably within
the 5-minute Edge Function ceiling.

\subsection{Recipe builder}

The Recipe Builder modal lives at \emph{Settings $\to$ Automations}
(admin-gated and \code{crm}-feature-gated). A recipe draft has the
shape:

\begin{lstlisting}[language=TypeScript]
interface RecipeDraft {
  name: string;
  enabled: boolean;
  trigger: { type: TriggerType; config: Record<string, unknown> };
  conditions: Array<{ field: string; operator: string; value: unknown }>;
  actions: Array<{ type: ActionType; config: Record<string, unknown> }>;
}
\end{lstlisting}

A live-run toast (Sonner) fires on every \code{automation\_runs}
INSERT via Realtime, so admins see recipes firing in real time across
their organisation.

\section{AI extensions}\label{sec:ai}

The automation engine is the substrate on which all AI features run.

\paragraph{AI Blocks.}

without an admin tap. Approval translates into a matching automation
action (e.g.\ \code{addNote} plus \code{sendEmail}).

\subsection{Telegram adapter}

\begin{itemize}
  \item \textbf{Authenticity.} Telegram echoes a secret in the
    \code{X-Telegram-Bot-Api-Secret-Token} header. The webhook URL
    additionally contains a path-segment secret.
  \item \textbf{Linking.} A 6-digit code generated in Settings,
    consumed via \code{/start <code>}.
  \item \textbf{Identity.} Telegram \code{user.id} stored as the
    \code{external\_id} on \code{integrations.metadata}.
\end{itemize}

\subsection{WhatsApp adapter}

\begin{itemize}
  \item \textbf{Authenticity.} HMAC-SHA256 of the raw request body,
    signed with the Meta App Secret, sent in
    \code{X-Hub-Signature-256}. Constant-time comparison.
  \item \textbf{Linking.} Same 6-digit code flow. Bot replies use
    interactive reply buttons (capped at three by Meta).
  \item \textbf{Identity.} E.164 phone number plus
    \code{current\_org\_id} on \code{integrations.metadata}.
  \item \textbf{Subscription.} Two distinct steps: App-level
    \code{messages} field subscription via Meta's UI; \emph{and}
    WABA-to-App subscription via
    \code{POST /v20.0/<waba\_id>/subscribed\_apps}. Missing the second
    step is the most common deployment failure mode.
\end{itemize}

\subsection{Confirm-before-write pattern}

Both adapters apply the same pattern:
\begin{enumerate}
  \item User sends a message.
  \item Webhook resolves the user, fetches a compact org-scoped
    context (workspace, project, client names), forwards to OpenAI.
  \item OpenAI returns a structured \code{Intent}.
  \item Resolver looks up entity ids; on ambiguity, returns a choices
    reply.
  \item On clean resolution, queues a row in
    \code{agent\_pending\_actions} (10-minute TTL) and replies with a
    Confirm / Cancel inline-button card.
  \item User taps Confirm. Webhook calls the matching
    \code{agent\_create\_*} RPC, deletes the pending row, replies with
    success.
\end{enumerate}

\section{Security and data handling}\label{sec:security}

\subsection{Authentication}

Firebase Auth provides identity. Tokens are exchanged for a Supabase
JWT signed with the project's anon key. Every PostgreSQL session
inherits the JWT's claims (\code{sub} mapped to \code{auth.uid()};
\code{role} set to \code{authenticated} for end users and
\code{service\_role} for Edge Functions using the service-role key).

\subsection{Row-Level Security}

Every domain table enables RLS. Writes either flow through a
\code{SECURITY DEFINER} RPC that re-checks membership using
\code{auth.uid()}, or are performed by the service role from an Edge
Function (where membership is re-checked via
\code{is\_org\_member\_for}). The browser never has a path to update a
row it could not also read.

\subsection{OAuth token storage}

Provider access tokens are encrypted at rest with AES-256-GCM
(\code{INTEGRATION\_TOKEN\_KEY}). The browser never receives the
plaintext. Edge Functions decrypt on demand for outbound calls and
refresh tokens within sixty seconds of expiry.

\subsection{Bot-specific guards}

\begin{itemize}
  \item Webhook signature verification, constant-time comparison on
    both Telegram and WhatsApp.
  \item Link codes are 6-digit, SHA-256 hashed at rest, single-use,
    10-minute TTL, five per hour per user.
  \item Service-role calls re-evaluate org membership before any
    write.
  \item Webhooks return \code{200} on internal exceptions to stop
    Meta and Telegram retry amplification; errors are surfaced via the
    chat reply or the Edge Function log.
\end{itemize}

\subsection{Workforce clock}

The \code{ClockGate} component forces every signed-in Admin or
Member to clock in before the app renders. Org Owners, Viewers, and
the app-owner role bypass. A 9-hour cutoff auto-closes any open
entry via the cron-scheduled \code{close\_stale\_time\_entries(9)}
function.

\section{Evaluation and future work}\label{sec:future}

\subsection{What this version delivers}

The current shipped surface includes: a complete project / task / file
/ comments / inbox system; a categorisable CRM with multi-pipeline
deals; an automation engine with eight triggers, nine action handlers,
template substitution, loop guards, and a live-run view; AI Blocks
registered as action handlers; an AI Sales Agent producing
review-gated suggestions; Telegram and WhatsApp chat-bot adapters
sharing a single \code{Intent} core; integrations with Google Calendar
/ Meet / Gmail and Slack; two graphical dashboards; a four-tier
subscription model; and a hardened security posture with RLS on every
table and AES-256-GCM-encrypted OAuth tokens.

\subsection{Known limitations}

\begin{itemize}
  \item Disambiguation callbacks in the chat-bot adapters
    (\emph{``Multiple projects match X. Pick one.''}) currently fall
    back to a rephrase prompt; the inline-button completion is a
    v1.1 polish.
  \item Plan-limit enforcement at the chat-bot RPC layer is best-
    effort; checks live in the front-end \code{usePlanLimits} hook.
  \item Per-user rate limiting on inbound chat-bot messages is not
    enforced; Meta and Telegram impose their own ceilings.
  \item Outside the 24-hour WhatsApp customer-service window, Meta
    requires pre-approved template messages. Initiated automations
    cannot push to a cold user until a template has been approved.
\end{itemize}

\subsection{Future work}

The roadmap is incremental rather than disruptive:

\begin{itemize}
  \item More trigger types in the automation engine: \emph{contract
    signed}, \emph{file uploaded}, \emph{contact added}.
  \item Promote the AI Blocks specification into shipped action
    handlers.
  \item Add wait / delay nodes to Sequences so true drip campaigns are
    expressible.
  \item Submit WhatsApp template messages for approval so the bot can
    initiate conversations outside the 24-hour window.
  \item Replace the EmailJS fallback path with the connected Gmail
    address for assignment notifications.
\end{itemize}

%  14. CONCLUSION
% ============================================================================
\section{Conclusion}

\tc{} is a layered product. Its base layer is a competent project-
management tool; its middle layer is a real CRM with categorisable
clients, multi-pipeline deals, lead capture, lead scoring, and
deal-scoped activity logging; its top layer is an automation engine
that ties everything together, fired by user actions, cron ticks, or
chat-bot messages and reaching out to Slack, Gmail, Google
Calendar/Meet, and arbitrary webhooks. Two chat-bot adapters sit
alongside, sharing a single \code{\_shared/agent} core so any
intent-parsing improvement upgrades both bots simultaneously.

Three architectural choices carry most of the system's robustness:

\begin{enumerate}
  \item RLS-first writes, with \code{SECURITY DEFINER} escape hatches
    only where strictly required.
  \item Confirm-before-write on the chat-bot path, so a language
    model can never write to the database without an explicit user
    tap.
  \item A single automation engine driving the AI Sales Agent,
    Sequences, and AI Blocks rather than three parallel pipelines.
\end{enumerate}

The product is ready for invitation-only customer pilots; the
remaining production gates are Meta's App Review for WhatsApp
Advanced Access and the UK Business Verification flow.
